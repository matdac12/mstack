# Review, merge, push, settle

## Review

Read the real diff (`git diff <defaultBranch>...<branch>`, `git log`), not the report. Check the claimed tests, that changed files stay within the owned files, that the worktree is clean and committed (`git -C <path> status --porcelain`), overlap with other unmerged branches and with what merged since the branch started (`git diff --stat $(git merge-base <defaultBranch> <branch>)..<defaultBranch>`: a rename or a changed signature there breaks a branch that never touched those files), and any warning the worker raised. A branch behind `<defaultBranch>` whose files are disjoint from what merged since: merge it directly (`git merge-tree --write-tree` must show no conflict; step 4's full check does the rest). Otherwise ask the worker for a rebase first. Execute-a-plan work is reviewed against the plan. A worker's report of a rejected command or a workaround is never a clean review: take it to Mattia before merging or pushing.

- **Weakened checks:** scan the diff for tests skipped or deleted, assertions removed or loosened, timeouts or thresholds raised, new allowlist or lint-disable entries, checks made non-blocking. Each one goes to Mattia before merge, like a rejected command.
- **Client repo and tracked docs:** the commit messages (`git log --format=%B <defaultBranch>..<branch>`) and the added lines of the diff hold no issue key (`grep -E '\b<PREFIX>-[0-9]+'` for each of the tracker's project keys) and no tracker name. Tracked docs (`CLAUDE.md`, `AGENTS.md`, `README.md`, `docs/**`) also hold no mention of Mattia's machines, local setup or personal skills (`/tracer`, `sub-tracer`, `superpowers`, `mattpocock-skills`, `unslop`, `grill-with-docs`, `to-spec`, `to-tickets`, `/implement`, `close-the-day`): those live only in untracked local files. A hit goes back to the worker.
- **Leaks, every repo:** `bash ~/.claude/skills/tracer/scripts/leak-check.sh <repo root> <defaultBranch>..<branch>` (env values, machine names, private patterns, and—in client repos—tracker names, personal skill names, `local/<branch>` refs, and any keys configured in `git config tracer.projectKeys`; it prints where, never the value; `land.sh merge` also runs it automatically). Machine names mean nothing to anyone else, and on a client repo they expose Mattia's setup. A hit goes back to the worker, who removes it from the branch's history (amend or rebase its own commits), never with a fix commit on top: the push would still carry it.
- **Fix work:** run the `Red first` test on the fix's parent commit when it is cheap; it must fail. A fix marked "hypothesis, not verified on <where>" merges as a fix only after you have told Mattia it is unverified there.
- **Skill:** the report's `Skill used` must match the brief's `Skill:` line; a swap goes to Mattia.
- **Docs:** check the report's `Docs touched` line against the diff; a user-visible change with "none" needs its why.
- **Pin the review:** the tracker comment recording the review names the branch SHA you reviewed.
- **Independent review brief:** include the base and reviewed SHA, supported inputs, invariants backed by constraints, contracts or tests, and realistic volumes and limits from the project's private notes. For a recheck, give the old and new SHAs, the accepted findings and any specific unresolved question. Review the fixes and regressions they could introduce. Widen the review if the fixes changed the original scope or an invariant.
- **Triage the findings** (yours, the worker's `code-review`, a second model's): **act now** (back to the worker before merge), **follow-up** (the task's follow-up issue), or **dismissed** with a one-line reason. Dismiss findings about code the branch did not write, cases the types or callers already rule out, and taste ("I would have done it differently"). A review that is all nits means the code is fine. Findings two reviewers raised independently come first.

Tell Mattia in a few lines what changed, the verification result, the act-now findings, how many you parked or dismissed, and your recommendation. Route manual checks to a separate Guide thread (kinds.md) once the required suite and review are green, fixes are integrated, and the exact candidate is available for checking.

## Merge

A yes naming the branches ("merge all three"), or a grant covering them (SKILL.md), counts once you have reviewed them and nothing alarms you; dirty main, red checks or out-of-boundary conflicts mean stop and ask. A yes to merge is never a yes to push. One branch at a time, in his order unless dependencies force another, else the larger first. Wait (`t3_thread_wait`) until the worker's thread is idle before touching its branch; never interrupt it.

1. **Preconditions, every time:** use the checkout on the agreed `<targetBranch>` (default, preview, integration or epic). Require a clean tracked tree and no merge or rebase in progress. If tracked changes exist, ask whether to commit or stash. Compare the source tip with the SHA recorded at review. If the tip moved, review the new commits first.
2. Write the merge message to a file (`m=$(mktemp)`, then a quoted heredoc into `"$m"`). Run `bash ~/.claude/skills/tracer/scripts/land.sh merge "<target checkout>" "<source branch>" "<reviewed SHA>" "$m"`. For a non-default target, prefix the same command with `TRACER_DEFAULT="<target branch>"`. For a remote source, append `<ssh> <root> <label>`. The script scans the pinned commit range and message, merges the reviewed SHA, and aborts on conflict. Run it as its own command and check its exit status before verifying the result. In a client repo the message describes the change without issue keys.
3. **Conflicts:** `git merge --abort` first (never leave main half-merged). Then **you** resolve them in the worker's idle, clean worktree: merge `<targetBranch>` into the branch, resolve only the conflicting hunks keeping both sides' intent, check no conflict markers remain, rerun the project's checks, commit, retry. Unclear intent, or files outside the task's boundaries: stop and ask.
4. **Verify** the merged result. Account for the full required suite, including typecheck, lint and service-gated variants the change touches. Check prior evidence before running it again:
   - **Reuse a check** only if its output shows it passed on a clean checkout of the identical Git tree (`git rev-parse <commit>^{tree}`), with the required command, platform, toolchain, configuration and service variants. Check the actual log or CI result. If the check depends on commit identity or history, require the exact commit. A skipped variant provides no evidence for that variant.
   - **Run uncovered checks.** A different tree needs fresh verification. Run the full required suite unless the project defines an affected-check policy that covers the integrated diff. If only some checks have matching evidence for the same tree, rerun the missing ones. Follow any gate that requires a fresh run or a specific environment. Record which results you reused and their source, and the command and exit code for new runs.
   - **Set up safely.** On a lockfile change, use the project's frozen install before running checks and refresh the linked machine's main checkout after syncing the real default branch. When verification needs the linked machine, test in a detached scratch worktree on the synced `local/<targetBranch>`, then remove it. Verify that database tests resolve to a disposable database and use a unique container name and loopback port. Use declared commands. If a required harness is unavailable, report the gap and ask before Done.
   - **Known-red baseline:** a check already red on a clean `<targetBranch>` has its failing tests listed by name on a tracker issue. The merge passes locally only if it fails exactly those, no new ones. It still counts as red for push (SKILL.md: red checks need Mattia's own yes), so name the baseline failures when you ask. No home-made lenient gate scripts; the real fix is an issue in the repo.
   - **Project-declared gate:** if the project's AGENTS.md or private notes declare a gate you cannot run locally (remote CI over SSH), follow it. When it needs a pushed ref, push only a temporary `ci/<short-sha>` branch (on his yes or grant: it is a network write), merge only when the `<targetBranch>` tree equals the tested tree, delete the `ci/` branch afterwards, and never push `<targetBranch>` just to test it.
5. **Green:** set the issue Done, or In Review with "hand check owed" (SKILL.md, Tracker discipline), then tell the others to rebase (below). **Red** (local or the declared gate): undo only this merge with `git revert -m 1 --no-edit HEAD`, then `git commit --amend -F "$m"` with a message saying why (never `reset --hard`, and never a fix merged on top), set the issue back to In Review or blocked with a comment, tell Mattia. Never leave `<targetBranch>` red for others to branch from. That worker gets no rebase notice: a rebase now silently drops its commits, because the reverted merge already contains them. Tell it instead: "your merge was reverted; fix on your branch and do not rebase". To merge it again, first revert the revert on `<targetBranch>` (or the worker cherry-picks its commits onto it), and `git diff <targetBranch>...<branch>` must not be empty. A branch reverted twice for the same check gets no third fix: write the premise both fixes shared on the issue and send an Investigate worker to test it. Still red after the revert: stop, tell him, and find the culprit among recent merges before merging more.
6. Only then the next branch.

## Integration rehearsal

Two finished branches touch the same files? Do not hand-test them one by one.
1. Detached scratch worktree, so no scratch branch needs deleting later: `git worktree add --detach ~/.t3/worktrees/<repo>/int-<ids> <defaultBranch>`, rerere on. Merge both with `--no-ff`; resolve conflicts there as in Merge step 3.
2. rerere replays conflict hunks, not semantic additions outside them (a new field a shared type also needs). Re-check the merged result compiles and passes the full checks, then build the release artifact. Prototype builds only when Mattia asks.
3. One Guide thread walks Mattia through the combined hand check on that build. On his yes, use Merge step 2 with the reviewed rehearsal commit SHA as both the source and reviewed SHA. Verify as in step 4, then clean up the worktree.

## Rebase notice (after each merge verified green)

First settle the merged worker's thread (Settle and clean up), so no notice reaches it. Then for every active worker based on the changed target whose branch still has unmerged commits (`git log --oneline <targetBranch>..<branch>` not empty), running or idle, except one whose merge was just reverted (step 5), `t3_thread_send`, mode per workers.md (Talking to a worker): "`<targetBranch>` moved: `<ISSUE>` is merged. When your current step is committed, rebase onto `<targetBranch>` and rerun your checks (worker-rules.md: which conflicts you resolve, and when you report)." Conflicts it aborts are yours at merge time (step 3). Launch no worker from `<targetBranch>` until the merge is verified green. A sub-tracer gets its own wording (subtracer.md).

## Push

Merge and verify everything locally. For a push requiring approval, use the approved remote and branch. If the push deploys, confirm the named environment in the approval or grant (SKILL.md, Grants).
1. Fetch the destination remote, resolve the verified local tip to a SHA, and show the outgoing commits. Use the remote-tracking tip of the destination branch as the base. For a new branch, use the remote default branch as the base.
2. **Leak check before every push**, including feature and `ci/` branches. Run `bash ~/.claude/skills/tracer/scripts/leak-check.sh "<repo root>" "<base>..<verified SHA>"` as a standalone command. Read the output and confirm exit 0 before pushing. Any other exit stops the push. On a hit, tell Mattia where and have the offending commit rewritten locally.
3. Push the checked SHA to the destination explicitly with `git push <remote> <verified SHA>:refs/heads/<destination branch>`. Never force.

Recommend CI when native or platform code changed (Rust, ...): it may be the only Linux check. Rejected or origin moved: merge or rebase locally, re-verify, show the revised set, ask again. Timeout: fetch and inspect before retrying. Feature branches you may push freely after the leak check (SKILL.md, Hard rules); no PRs unless he asks.

"Push without CI" means `[skip ci]` in the **head** commit message. Prefer an empty commit (`git commit --allow-empty -m "<IDS>: push ... [skip ci]"`; no `<IDS>` in a client repo) to amending a merge commit: amending changes SHAs that sub-tracers or workers may already have been told about.

## Settle and clean up

Automatic, without being asked, for threads you launched only (never another orchestrator's).

**Settle** a thread the moment it is no longer needed: `t3_thread_organize {"action":"settle","threadId":"<id>"}` (reversible with `unsettle`; archive only if he asks).
- Implement, fix and execute threads: once their merge is verified. One that started a preview it still owns, for a hand check: only once Mattia confirms that area of work is done, because settling it kills what he is looking at. A preview running as its own service (a systemd unit) does not hold the thread.
- Review and investigate threads: once the report is recorded.
- Design and interview guide threads: once the execution thread is launched from their plan, or the design is dropped. Keep the worktree until the merge.
- Hand-check guides: once the outcome is recorded and Mattia has finished using any preview the guide owns.
- Cancelled or abandoned threads: right away.

Settle the thread's subagents with it: find them with one `t3_thread_list {"settled":false,"includeSubagents":true}` and settle them in parallel batches. A settle fails while the thread's turn is still running: `t3_thread_wait` it first. **Never** settle a thread that is running, has a pending request, has an unrecorded report, or owns an unmerged branch (a design thread whose branch moved on to an execution thread does not); so never a running sub-tracer or its active workers. Tell Mattia in one line what you settled.

**Clean up** each finished task's worktree yourself, in this order, as one step with the settle (a running thread, dev server or `agent-browser` daemon locks the folder on Windows):
1. Settle its threads, and stop any dev server or orphaned browser daemon (`agent-browser`, headless `chrome`/`chromium`) running from that worktree (find it with `Get-CimInstance Win32_Process` filtered on the path in `ExecutablePath` or `CommandLine`; never stop `claude.exe`).
2. `git -C <path> status --ignored`: copy out anything gitignored the report names (backups, artifacts).
3. `bash ~/.claude/skills/tracer/scripts/cleanup-task.sh <repo root> <path> <branch> <defaultBranch>`: the one cleanup path. It refuses unless the worktree is under `~/.t3/worktrees`, fully committed, and its branch merged. Its new untracked `.env*` files (a password the worker generated) go to that machine's main checkout first. An env file main already has must keep the same keys, and the same values for the shared keys the project's private notes name (set them as `git config tracer.sharedEnvKeys "<KEY> <KEY>"`); a per-worktree value (a database name, a port) passes. Copy a new file into your own main checkout too (over SSH for a remote worker), so the leak check knows its values. Then it removes the worktree, its leftover dependency folders (junctions unlinked, never followed) and the branch. `--drop-db <name>` (the task's scratch database, from the report) goes with the cleanup of every merged task with no hand check owed; the script drops only names with the configured prefix. On Mattia's yes only: `--force-unmerged` (an unmerged branch; it prints the tip), and `--drop-db` for an unmerged task or one with a hand check owed. The drop command comes from the repo's git config (`tracer.dropDbCommand`, with the name prefix in `tracer.scratchDbPrefix`), which Mattia sets from the project's private notes; it is never typed on the command line. On a linked machine, merged branches only: `ssh <ssh> bash -s -- <root> <path> <branch> local/<defaultBranch> < ~/.claude/skills/tracer/scripts/remove-worktree.sh`; it fast-forwards that checkout's `<defaultBranch>` first when `<defaultBranch>` is the repo's real default branch, so the branch delete sees the merge.
4. A refusal: tell Mattia its one line and leave that worktree. Never delete another way. Remove a merged branch on origin only with his OK. Your report to Mattia at the end of each task lists every cleanup command still blocked, with the exact command for him to run (valid PowerShell on Windows: workers.md, Windows / Git Bash); the close-of-day note repeats it.

## Deploy

Only when Mattia asks for it explicitly (a grant never covers it), with the project's documented procedure, from the clean main checkout; long steps in the background. Verify health and report the version.
